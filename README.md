# astrbot_plugin_airi_core

Airi 的 AstrBot 辅助核心插件，提供群管理、好友/群邀请审批、入群欢迎与 Poke 统计排行榜等功能。

## 功能

- 可配置 `@Bot` 唤醒 LLM：即使设置了 provider wake prefix，也可以通过直接 @Bot 进入人格对话，并复用当前会话上下文。
- 可配置 LLM 主动 @ 群友工具：只有模型判断确实需要明确点名某位群友时才会 @，普通回复不会自动 @。
- LLM 群禁言工具，可配置允许的禁言时长范围。
- 可选自动同意 OneBot / aiocqhttp 的 QQ 好友申请。
- 可选好友申请 / 邀请 Bot 入群人工审批：请求会私聊发送给指定 QQ，由指定 QQ 决定同意或拒绝。
- 兼容 Snowluma 将好友申请上报成普通私聊“请求添加你为好友”的情况，无需修改 Snowluma / OneBot / AstrBot 内部代码。
- Bot 加入新群时发送自定义欢迎文字与图片。
- 记录群友“戳一戳” Bot 的次数，每个 QQ 独立累计。
- 提供每日当前群榜、每日所有群总榜，以及两套历史累计榜。
- 每日榜以服务器本地时间 **04:00** 为统计日切换点，不依赖定时任务清空数据。
- 当前群日榜与历史榜将“本群总次数 / 参与用户 / 群排名”放在底部统计卡中；顶部仅保留榜单类型与 04:00 刷新提示。
- Poke 排行榜使用粉白 / 紫粉渐变卡片生成 PNG 图片，前三名突出显示，并为每个上榜 QQ 显示圆形头像。
- QQ 头像通过公开 qlogo 地址获取并在本地缓存 24 小时；网络失败时优先使用旧缓存，没有缓存则绘制默认占位头像。
- 排行榜图片不展示完整 QQ 号：当前群优先显示群名片，其次 QQ 昵称；总榜显示 QQ 昵称；获取失败时使用匿名代号。
- Poke 数据持久化保存，AstrBot 重启或插件重载后不会丢失。
- 可选 QQ 空间好友新说说自动点赞（SnowLuma / OneBot；默认关闭），含只读测试、好友分批扫描、首次索引、去重、限频及风控暂停。

## @Bot 唤醒 LLM
### v1.3.10：@Bot 多模态修复

- 使用 `@Bot + 图片 + 文字`、`@Bot + 图片`、`引用图片后 @Bot 提问`，现在会收集当前消息和引用消息中的真实图片路径并随同一个 LLM 请求发送。
- 先使用 AstrBot 预处理过的 `Image.convert_to_file_path()` 获取直传/引用链中的图片；引用消息只有 ID、`[图片]` 占位或引用链图片获取失败时，才按需使用 AstrBot 官方 `extract_quoted_message_images` 解析 OneBot `get_msg` 等引用来源。
- 一次请求最多收集 12 张图片，重复图片引用去重；单张失败不阻塞其他图片。若引用显示为图片却确实无法读取，会告知用户重新发送原图，不会假装识图成功。
- 保留当前 conversation、人格、工具调用与单次 LLM 请求，不增加系统提示词或额外模型调用。没有明确 @ Bot 时不触发。无需修改 AstrBot 核心或图片数据。


v1.3.7 起增加可配置的 `@Bot` 唤醒功能。

当 `self_mention_wakeup_enabled=true` 时，在 QQ / OneBot 群聊中发送：

```text
@Bot 你好
```

插件会检测消息链中是否真的 @ 了 Bot 自己，并显式触发一次 LLM 请求。因此，即使 AstrBot 的 provider wake prefix 配置为 `ch`，`@Bot 你好` 仍可以进入人格对话。

该功能会复用当前 AstrBot conversation，不额外注入 `system_prompt` 或重复拼接人格内容；如果当前还没有 conversation，则按 AstrBot 的会话管理方式创建一个。这样可以尽量保持原有上下文与模型缓存行为，避免因为 @ 唤醒单独构造一套大 Prompt。

为了避免重复请求，@ 唤醒触发显式 LLM 请求后，会阻止同一条消息继续进入 AstrBot 默认 LLM 链路。

规则：

- `@Bot + 文本`：触发 LLM。
- 仅 @ 其他群友：不触发。
- 没有 @Bot：不受该功能影响。
- 仅发送空 @ 且没有附件：不会额外调用 LLM；带有图片的 @ 即使没有文字也能发起识图请求。
- `self_mention_wakeup_enabled=false`：完全关闭此功能，恢复为 AstrBot 原有触发方式。

## LLM 主动 @ 群友

v1.3.8 起增加可配置的 `mention_user` LLM 工具。

当 `mention_tool_enabled=true` 时，LLM 可以在确实需要明确点名、提醒某位群友，或多人同时聊天需要明确指向时调用该工具。普通聊天不需要调用，因此不会变成每条回复都自动 @ 发送者。

工具流程：

1. LLM 调用 `mention_user(user_id=...)`。
2. 插件确认当前为 OneBot 群聊、QQ 号合法、目标不是 Bot 自己，并通过 `get_group_member_info` 确认目标在当前群。
3. 工具只把目标 QQ 记录到当前事件中。
4. 最终回复进入 `on_decorating_result` 时，插件在消息链最前面插入真实 `At` 消息段。
5. 如果最终消息链已经 @ 了同一个人，则不会重复插入。

为了尽量保持 LLM 缓存稳定，这个功能不会在每轮请求里动态修改 `system_prompt`，也不会额外拼接动态上下文。启用时只会增加一个固定的工具 schema；关闭 `mention_tool_enabled` 后该工具不会注册，也不会产生这部分工具 schema 开销。

## 好友申请与群邀请

v1.3.5 起，请求事件按照 AstrBot aiocqhttp 的请求处理方式独立监听，不再混在 notice/Poke 事件处理器中；审批动作直接使用 CQHttp 提供的 `set_friend_add_request` 与 `set_group_add_request`。

v1.3.6 起增加 Snowluma 好友申请兼容：部分 Snowluma 版本不会向 AstrBot 上报 OneBot `post_type=request`，而是把好友申请转换成申请人的普通私聊文本 `请求添加你为好友`。插件会仅在 aiocqhttp 私聊、且文本完全匹配该系统提示时启用兜底，并使用消息发送者 QQ/UIN 调用 Snowluma 已提供的 `set_friend_add_request`。识别后会停止该系统消息继续进入其他插件或 LLM。

此兼容逻辑只位于 Airi Core 插件内部，不需要修改 Snowluma、OneBot 或 AstrBot。

### 自动同意好友申请

在插件配置中开启 `auto_accept_friend_request` 后：

- 标准 OneBot：收到 `post_type=request`、`request_type=friend` 的好友申请时，直接调用 `event.bot.set_friend_add_request(..., approve=True)`。
- Snowluma 兼容：收到申请人的私聊系统文本 `请求添加你为好友` 时，以发送者 QQ/UIN 作为 `flag` 调用同一个 `set_friend_add_request`。
- 该选项默认关闭。
- 只自动处理好友申请，不自动同意群邀请。
- 若同时开启人工审批，**好友申请优先自动同意，不再发送审批通知**；群邀请仍然走人工审批。

### 人工审批

配置：

- `request_approval_enabled=true`
- `request_approval_qq=你的审批 QQ 号`

开启后，需要人工处理的好友申请以及邀请 Bot 入群请求会私聊发送到指定 QQ。Snowluma 好友申请兜底模式下，如果上游没有提供验证信息，通知中会显示 `Snowluma 未提供验证信息`。

每个请求都有独立编号，例如：

```text
【好友申请】A001
昵称：示例用户
QQ：123456789
验证信息：你好

回复 /同意申请 A001 或 /拒绝申请 A001
```

群邀请会同时显示邀请人、群名称与群号。

只有配置的 `request_approval_qq` 有权限执行：

| 指令 | 说明 |
| --- | --- |
| `/同意申请 A001` | 同意对应好友申请或群邀请 |
| `/拒绝申请 A001` | 拒绝对应好友申请或群邀请 |

处理规则：

- 好友申请：调用 `set_friend_add_request(flag=..., approve=...)`。
- 群邀请：调用 `set_group_add_request(flag=..., sub_type="invite", approve=...)`。
- 审批成功后，对应待审批记录立即删除。
- OneBot 审批失败时保留记录，可以稍后再次执行审批命令。
- 非指定 QQ 执行审批命令会提示无权限。
- 待审批信息会持久化，因此 AstrBot 重启后仍可继续处理。

待审批数据保存在：

```text
data/plugin_data/astrbot_plugin_airi_core/pending_requests.json
```

## Poke 排行榜

### 指令

| 指令 | 说明 |
| --- | --- |
| `/poke排行` | 当前统计日当前群榜，默认显示前 10 人 |
| `/poke排行 50` | 当前统计日当前群榜，显示前 50 人 |
| `/poke排行 123456789` | 兼容旧写法：默认显示前 10 人，并查询指定 QQ |
| `/poke排行 50 123456789` | 显示前 50 人，并查询指定 QQ |
| `/poke总排行 [人数] [QQ]` | 当前统计日所有群合计总榜；人数和 QQ 均可选 |
| `/poke历史排行 [人数] [QQ]` | 当前群历史累计榜；人数和 QQ 均可选 |
| `/poke历史总排行 [人数] [QQ]` | 所有群历史累计总榜；人数和 QQ 均可选 |
| `/poke群排行 [人数]` | **跨群日榜**：按各群今天戳 Bot 的总次数排名 |
| `/poke历史群排行 [人数]` | **跨群历史榜**：按各群从启用以来戳 Bot 的总次数排名 |

六个排行命令都遵循相同规则：不写数量时默认显示前 **10** 名；填写数量时最多显示到配置项 `poke_rank_max_limit` 指定的上限。请求人数/群数超过上限时会自动按上限生成。群聊排行榜只接受可选的排名数量，例如 `/poke群排行 50`。

### 跨群 Poke 排行（v1.3.12）

`/poke群排行` 统计的是**各个 QQ 群里，群成员戳 Bot 的总次数**，不是群友互戳次数；`/poke历史群排行` 统计同样指标的历史累计。

- 每个群单独占一名，按次数从高到低排名；次数相同时按群号稳定排序。
- 图片展示群名、群号、被戳次数；先从 OneBot 群列表读取群名，无法读取时进一步查询群信息，仍失败则使用“未知群聊 + 群号”。
- v1.3.13 起，每个显示在群榜中的群会额外展示圆形 QQ 群头像；使用 `https://p.qlogo.cn/gh/{群号}/{群号}/100` 获取，只下载实际展示的群头像，最多 5 个并行请求。
- 默认显示 10 个群，`/poke群排行 50` 显示前 50 个群（受现有最大人数配置限制）。
- 只使用已有 `poke_stats.json`，无需迁移数据；历史群榜保留旧版本累计数据，日榜遵循现有 04:00 切日规则。
- 群头像缓存与用户 QQ 头像分开存储，默认有效 24 小时；下载失败优先使用旧缓存，否则显示占位图。不会将群号误当 QQ 用户号，也不会额外触发 LLM。

### 每日刷新规则

每日榜不是通过一个必须在 04:00 准时运行的定时任务去清空，而是使用“统计日”计算：

```text
统计日 = 当前服务器本地时间 - 4 小时 后对应的日期
```

因此：

- 09 月 20 日 03:59 仍属于 09 月 19 日榜。
- 09 月 20 日 04:00 起进入 09 月 20 日榜。
- 即使 AstrBot 在 04:00 时离线、重启或插件没有运行，下一次记录/查询时仍会自动进入正确的新统计日。
- 切日影响 `/poke排行`、`/poke总排行` 和 `/poke群排行`；历史累计榜不会清零。

从 v1.2.x 升级时，旧 `poke_stats.json` 中的累计次数会完整保留到历史榜。由于旧版本没有记录每次 Poke 的日期，升级前的历史累计数据不会被错误塞进升级当天的日榜；日榜从 v1.3.1 开始按新规则记录。

### 统计规则

只有 OneBot / aiocqhttp 上报的群内 Poke，且被戳目标 `target_id` 等于 Bot 自己的 QQ 时才会计数。因此：

- 群友戳 Bot：计数。
- 群友互相戳：不计数。
- Bot 自己触发的 Poke：不计数。
- 当前群榜按群分别统计。
- 总榜把同一个 QQ 在所有群中的次数相加。

### 头像与隐私展示

统计内部仍以 QQ 号作为稳定用户标识，以保证跨重启、跨群汇总时不会因为昵称变化而把同一用户拆成多人；**完整 QQ 号不会绘制到排行榜图片中**。

- 当前群榜：`群名片 > QQ 昵称 > 匿名用户代号`
- 所有群总榜：`QQ 昵称 > 匿名用户代号`
- 每个实际显示在榜单中的用户会尝试加载其 QQ 头像，并裁剪为圆形显示在昵称左侧。
- 头像缓存默认有效 24 小时；过期后会尝试刷新，刷新失败时仍可继续使用已有缓存。
- 无可用头像时显示默认占位头像，排行榜仍可正常生成。
- 当前群排行榜图片不会显示群号。
- 昵称过长会自动截断，避免破坏卡片排版。

Poke 数据保存在：

```text
data/plugin_data/astrbot_plugin_airi_core/poke_stats.json
```

QQ群头像缓存保存在：

```text
data/plugin_data/astrbot_plugin_airi_core/group_avatar_cache/
```

QQ 头像缓存保存在：

```text
data/plugin_data/astrbot_plugin_airi_core/avatar_cache/
```

生成的排行榜图片也会临时保存在插件数据目录，插件会自动清理较旧图片，只保留最近一部分。

## 插件配置：按功能分组

从 v1.3.15 起，插件配置面板按 6 个区块展示，使用 AstrBot 官方 `object` 分组：

| 分组 | 主要配置 |
| --- | --- |
| AI 对话与互动 | @Bot 唤醒、LLM 主动 @ 群友 |
| 群管理与禁言 | LLM 禁言开关、禁言时长范围 |
| 入群欢迎 | 欢迎开关、文字和图片 |
| 好友申请与群邀请 | 自动通过好友、人工审批和审批 QQ |
| 戳一戳与排行榜 | 统计开关、排行榜上限 |
| QQ 空间自动点赞 | 点赞总开关、扫描间隔、每轮数量；其他选项收在「高级设置」 |

升级时，插件会将以前的扁平配置字段迁移到新分组，保留已经设置的自定义值；旧字段仅为升级兼容保留，不再出现在表单中。迁移成功后会记录标记，防止后续重启覆盖新分组的修改。不要直接删除旧配置文件。

QQ 空间点赞的机器人 QQ 号**不再需要填写**：插件从当前 QQ/OneBot 事件获得 `self_id` 并绑定该会话，后续收到其他账号的事件不会误切换账号。如果同一 AstrBot 同时连接多个机器人账号，首次触发绑定的账号会优先使用；目前还没有多账号选择器。
## QQ 空间好友自动点赞（v1.3.18）

该功能直接集成于 Airi Core 的 `qzone_auto_like.py`，无需额外安装点赞插件或 NapCat。使用 SnowLuma / OneBot 的 `get_friend_list` 与 `get_cookies(domain="user.qzone.qq.com")`。不落盘保存 QQ 空间 Cookie，也不会在日志中输出完整 Cookie。

**默认关闭自动点赞，开启即真实点赞。** `qzone_auto_like_enabled=false`、`qzone_dry_run=false`。首次扫描结合发布时间，避免给启用前的历史说说批量补赞；符合条件的新动态会加入持久化待点赞队列。只读测试期间发现的动态不会在切换至真实点赞后追补。

### 原理及限制

- 每轮获取一次当前 QQ 的好友动态流，并轮换扫描最多 8 位好友的 QQ 空间，尝试覆盖好友动态流遗漏的作者。仅处理 QQ 好友发表的 mood 说说，忽略自己和非好友动态。
- 每次扫描间隔默认 300 秒，**每轮最多实际尝试点赞 3 条，但会完整收集本轮发现的新动态**；实际点赞前随机延迟 15–30 秒。
- 点赞时使用动态页面的 `http://user.qzone.qq.com/.../mood/...` 标识；POST 返回 `code=0` 之后还会只读查询 `is_dolike`，**只有确认当前机器人确实已点赞才计为成功**。QQ 空间读取点赞状态可能限流，无法核验时不会误报成功。
- 对首次扫描的好友使用说说发布时间判断是否属于启用后的新动态；发布时间不明确时保守建立历史索引，避免误赞旧动态。
- 每条新动态先持久化入队，重启后仍在队列中；即使之后被好友动态流挤出也能按序处理。真正点赞前先只读确认账号是否已点赞，避免重复点赞。
- 请求失败或核验失败时保留队列并退避重试，自动 POST 最多尝试 3 次；连续失败任务不会删除，而是暂停自动重试并在 `/空间点赞 状态` 中展示，需人工检查。若接口状态无法确认，则不发送点赞请求。
- 单次待处理队列最多保留 2,000 条，达到容量时告警并保留未处理动态的下轮重扫机会；本功能不保证覆盖 QQ 空间未返回的动态。
- HTTP 401/403/429 或检测到明显的登录验证响应时暂停一小时，不绕过验证码。
- QQ 空间使用非官方接口，访问权限、动态流内容和页面结构可能变化，**不能保证 100% 覆盖所有好友的新动态**。

### 配置选项

| 配置项 | 默认值 | 作用 |
| --- | --- | --- |
| `qzone_auto_like_enabled` | `false` | 总开关：开启后自动点赞 |
| `qzone_dry_run` | `false` | 高级选项：只读测试，不发送点赞 |
| `qzone_owner_qq` | 空 | 允许管理命令的 QQ；留空则不允许命令控制 |
| `qzone_poll_interval_sec` | `300` | 扫描间隔，最低 120 秒 |
| `qzone_friend_batch_size` | `8` | 每轮额外扫描多少好友空间 |
| `qzone_feed_count` | `30` | 每来源请求的动态数量 |
| `qzone_max_likes_per_cycle` | `3` | 每轮最多尝试点赞数，超出的新动态保存到待处理队列 |
| `qzone_delay_min_sec` | `15` | 点赞前随机延迟最短秒数 |
| `qzone_delay_max_sec` | `30` | 点赞前随机延迟最长秒数 |

只有配置的 `qzone_owner_qq` 可以使用以下指令（需要 QQ/OneBot 消息）：

- `/空间点赞 状态`：查看运行状态、已发现好友、索引数、待点赞数量及暂停重试数量。
- `/空间点赞 开启`：本次运行中开启；重启后仍以插件配置为准。
- `/空间点赞 关闭`：本次运行中停止。
- `/空间点赞 扫描`：立即扫描并处理一轮队列，返回新发现、入队、尝试、确认成功、失败及剩余待处理数。内部加锁防止并行扫描。

首次调试可临时打开高级设置中的 `qzone_dry_run=true`，扫描只建立索引而不点赞；正常使用无需勾选。该功能的去重状态保存于 `data/plugin_data/astrbot_plugin_airi_core/qzone_auto_like.json`，不包含 Cookie 和好友说说正文。

QQ 空间请求字段参考 MIT 许可证项目 [cube-lover/astrbot_qzone_auto_like](https://github.com/cube-lover/astrbot_qzone_auto_like)，许可证保留于 [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)。

### 首次扫描与旧索引补漏（v1.3.17）

- 首次扫描不再无条件把该好友的所有动态当作历史。优先解析 QQ 空间 `feed_data` 的 `data-uin`、`data-tid`、`data-abstime`，按作者、说说 ID、发布时间精确对应。
- **只有发布时间不早于本功能首次启用时刻的说说**才会在首次扫描时作为新动态处理；已存在的旧说说仍不补赞。发布时间无法可靠获取时保持保守的历史索引逻辑。
- 兼容升级前的旧去重数据：若一条已索引说说确实发布于首次启用之后，并且没有记录过本次补漏的处理结果，会先通过只读接口确认是否已经点赞。已点赞直接跳过；未点赞且接口有效时才尝试点赞一次。
- 每轮最多执行 5 次旧索引的只读点赞状态核验；仍沿用“每轮最多处理 3 条”的数量限制。只处理最近 24 小时发布的说说，避免离线很久后补赞很旧的内容。
- 保存 `started_at` 和 `resolved` 状态，避免插件重启后反复补漏。对 v1.3.16 的旧数据，首次启用时刻从已有说说索引最早记录时间推断。
- `/空间点赞 扫描` 增加“旧索引补漏”“已点赞跳过”的可读统计，方便确认是没有新说说还是被去重跳过。

这次修改**不会批量补赞启用之前已经发布的说说**。若需要人工指定补赞更早的历史动态，应另行设计明确的范围和确认机制。

### 持久化待点赞队列（v1.3.18）

- 扫描与实际点赞拆为两步。扫描首先把所有符合条件的新说说加入 `pending`，随后只从队列中按发现顺序取最多 `qzone_max_likes_per_cycle` 条执行点赞。示例：一次发现 8 条时默认先处理 3 条，之后各轮处理 3、2 条，即使后续 QQ 空间动态接口不再返回这些说说，待办也不会直接丢失。
- 队列保存在原有 `qzone_auto_like.json` 中，只记录好友 QQ、说说 ID、发布时间、入队时间、尝试次数和下次重试时间；不存 Cookie 或说说正文。旧版 `seen/resolved/started_at` 自动兼容，无需清空历史数据。
- 每轮点赞前都只读检查 QQ 空间 `is_dolike`；已经点赞则标记完成，未点赞才发送。POST 返回成功后仍进行二次只读核验。若失败，记录尝试次数，至少等待 5 分钟后再试；最多自动提交 3 次，达到上限时任务保留但不再自动重试，避免持续触发风控。
- 只读测试模式中新加入队列的动态会标记为仅测试，后续关闭只读测试也不会误触发真实点赞。账号切换时清除旧账号状态，防止跨 QQ 账号混用。
- 定时周期是扫描结束后再等待 `qzone_poll_interval_sec`，不是严格每 300 秒整点运行。如果大量动态或接口较慢，排空队列可能需要多轮。
- 只保证已成功扫描并加入队列的动态不因被动态流挤掉而丢失；无法保证 QQ 空间接口把全部好友说说返回，也不能保证 QQ 服务器实际点赞一定成功。
